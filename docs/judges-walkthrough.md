# Защита за три минуты

Показываем один законченный путь: выбранная ВЭС → почасовой прогноз → анализ
агента → проверяемые результаты модели → воспроизводимый экспорт. Первую
демонстрацию проводим на явно обозначенных синтетических данных; реальные
январские метрики показываем отдельно, с их ограничениями.

## Подготовка с чистого клона

Нужны Node.js 22.12+ и uv. Из корня репозитория:

```sh
uv sync --locked
npm ci
npm run check
npm run dev
```

Открыть http://127.0.0.1:5173. В другом терминале проверить полный HTTP-сценарий:

```sh
uv run python scripts/smoke_demo.py
```

Проверка создаёт локальные DEMO-записи: прогноз двух турбин на 48 часов,
проверку неизменных входов, 29 ежедневных выпусков и февральский CSV. Она
проверяет интеграцию, а не конкурсную точность. Открыть заранее Explore,
Forecast и Evidence (экран Model evidence); не запускать обучение во время
трёхминутной защиты.

Model evidence получает сохранённый отчёт через `GET /api/v1/evidence`;
кнопка Download evidence выгружает JSON через `/api/v1/evidence/export`.
Он доступен без локальных обученных весов. Просмотр отчёта не является повторным
обучением: для воспроизведения подготовки, хронологического выбора и регистрации
новой модели использовать [точные команды обучения](ml-training.md#chronological-model-selection).
Исходные CSV, версии зависимостей, параметры, часы доступности и контрольные
суммы должны соответствовать отчёту; локальные идентификаторы моделей могут
отличаться. Подготовка и обучение выполняются до показа.

### Однократный цикл получения погоды

Для уже успешного прогноза можно проверить обновления без постоянного watcher:

```sh
uv run python -m wind_agent.worker --run-id run-REPLACE --once
```

Чтобы сначала автоматически скачать погодного кандидата для каждой турбины
выбранного запуска, явно указать цикл модели в UTC. Например, для прогноза,
выпущенного 31 января 2026 в 00:00 UTC:

```sh
uv run python -m wind_agent.worker --run-id run-REPLACE --once --fetch-run-init 2026-01-31T00:00:00Z
```

Сервер делает внешний запрос через существующий `/weather/fetch`. Доступность
источника и конкретной даты не гарантируется; для защиты этот шаг лучше
выполнить заранее. Worker не угадывает цикл, время публикации или статус
проверки: возвращённые снимки должны быть `unverified`, без `available_at` и
доказательства публикации. Их ID и статус попадут в JSON-отчёт. Затем обычный
`refresh` проверяет допустимые входы исходного запуска: архив выбирает только
отдельно проверенные снимки, demo остаётся синтетическим. Поэтому скачивание
кандидата само по себе обычно даёт `changed=false`.

Код выхода `0` означает, что цикл проверки выполнен; если новый прогноз
поставлен в очередь, отчёт явно содержит `forecast_status=queued`, а не обещает
готовый результат. Ошибка даёт код `1`; при неудачной загрузке refresh не
выполняется, ID уже полученных кандидатов сохраняются в отчёте. Неверные
аргументы дают код `2`. `--fetch-run-init` требует `--once`, чтобы не скачивать
один и тот же неизменяемый архив бесконечно. Прежний watcher без этих флагов
продолжает проверять выбранный запуск с заданным интервалом.

Это ограниченная автоматизация получения кандидатов и проверки входов, не
автоматическое подтверждение происхождения и не полный февральский replay.
Проверки `tests/test_worker.py` используют подставной погодный ответ и работают
без внешних погодных запросов.

обслуживанию и не доверительный интервал. Среднее по турбинам не является
физической мощностью станции: номиналы турбин не заданы.

На **странице 1** обязательны самостоятельное получение открытых погодных
прогнозов по координатам, полный цикл «получение → подготовка → прогноз →
анализ → пересчёт» и исторический февральский replay с погодой, доступной на
момент каждого выпуска. Отдельного балла за MAE и обязательного требования LLM
в документе нет. Улучшение ошибки служит доказательством качества подхода.

## Что можно утверждать о реальной модели

- Победитель выбран по ноябрьскому и декабрьскому хронологическим окнам.
  Январь не участвовал в этом поиске, но уже просматривался для исходной модели;
  это повторно использованный период сравнения, а не нетронутый тест.
- Январская оценка относится к модели с cutoff **1 января 2026, 00:00 UTC**:
  MAE 0,28006, RMSE 0,33508, 2 688 оценённых пар и ноль пропущенных фактов.
  Перекрывающиеся выпуски коррелируют; это не 2 688 независимых испытаний.
- Улучшение MAE составляет 6,13% относительно предыдущего CatBoost и 18,49%
  относительно persistence. MAE 0,28006 — ошибка на шкале [0,1], не «точность 72%».
- Отдельное дообучение с cutoff **31 января** имеет другие веса. Январские метрики
  нельзя приписывать этим весам; измеренного февральского результата у них нет.
- Владелец проекта подтвердил фиксированный UTC+06:00, начало 10-минутного
  интервала и нормализованную мощность. Старые артефакты сохраняют записанные
  при обучении допущения, включая непроверенное определение нормализации и
  задержку доступности 10 минут. Новое подтверждение не меняет их происхождение
  задним числом. Задержка SCADA всё ещё требует подтверждения; результаты
  остаются provisional. Номинальная мощность и высота ступицы не заданы.

[исходный JSON отчёта](model-selection-results.json),

## Что ещё мешает полному выполнению кейса

1. **Доказанный погодный архив за февраль.** Для каждого выпуска и турбины нужны
   исходный операционный прогноз, его цикл, подтверждение времени публикации и
   полное покрытие часов. Скачанный сегодня hindcast и свободный текст
   `availability_evidence` сами по себе не доказывают историческую доступность.
2. **Непрерывное автоматическое получение и обновление.** Worker умеет за один
   ограниченный цикл скачать кандидатов для явно указанного выпуска и проверить
   обновления выбранного прогноза. Архивный агент выбирает уже проверенные снимки.
   Это ещё не автономный сервис, который сам обнаруживает новые выпуски,
   подтверждает их происхождение и запускает ежедневные прогнозы. Проверку
   происхождения нельзя подменять присвоением всем скачанным данным verified.
3. **Проверенный конечный февральский результат.** Требуется прогнать модель с
   допустимыми входами и экспортировать весь период. Без февральских фактов можно
   создать прогнозы, но нельзя измерить февральские MAE/RMSE. Также нужно явно
   зафиксировать расписание выпуска и границы часовых интервалов; 07:00 UTC —
   решение команды, а не заданное в кейсе время.
